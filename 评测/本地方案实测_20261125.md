> 时间：2026-11-25 13:39–13:57 ｜ 触发：用户裁定「N2 改走视觉方案」后追问「GitHub 上有没有可以直接用、不需要调其他接口的方案」

## 0. 结论先说

| 方案 | 能否直接用 | 需外部接口 | 需装 Python 包 | 读斜率 | 读截距（外推） | 单张耗时 |
|---|---|---|---|---|---|---|
| **llama.cpp + Qwen2.5-VL-3B** | **能，已跑通** | **否** | **否** | **✓ 全对** | **✗ 直接问会错；分步喂点则对** | 40–56 s（CPU，含每次重载模型） |
| 纯 PIL 像素扫描 + 最小二乘 | 能（本次自写 60 行） | 否 | 否（仅用已装的 Pillow） | ✓ 误差 0.4% | ✓ 误差 1.0% | < 1 s |
| plotdigitizer（PyPI） | **不能** | 否 | 是（numpy/scipy） | — | — | 装不上，见 §4 |
| deepseek-chat 视觉 | 已验可行 | **是** | 否 | 未验读数 | 未验 | 取决于网络 |

**一句话**：本地跑得起来，而且不用调任何接口；但它不是「问一句就给答案」，必须把读图拆成步骤。真要精确数值，纯像素扫描比 3B 模型准一个量级。

## 1. 为什么之前卡住、现在通了

两个硬约束是本机实测出来的，不是查资料得出的：

| 约束 | 实测结果 |
|---|---|
| GPU | `nvidia-smi` **不存在**；显卡是 AMD Radeon 780M 核显（无 CUDA） |
| 内存 | **13.8 GB** |
| CPU | AMD Ryzen 7 8845H，8 核 16 线程（Zen4，llama.cpp 自带 `ggml-cpu-zen4.dll`） |
| Python 包 | torch / transformers / numpy / cv2 / onnxruntime **全部未安装**；`pip install numpy` **被本机安全策略拦截**（见 §4） |
| Python 版本 | 3.13.14（很新，部分包无轮子） |

所以凡是「要 pip 装 numpy/torch」的方案，本机都走不通。剩下的路只有一条：**不依赖 Python 生态的原生二进制**。

## 2. llama.cpp + Qwen2.5-VL-3B（推荐方案）

### 2.1 装了什么、多大

| 组件 | 来源 | 体积 |
|---|---|---|
| `llama-b12716-bin-win-cpu-x64.zip` | `github.com/ggml-org/llama.cpp` releases（官方预编译，**不用编译**） | 25 MB，解压 64 MB |
| `Qwen2.5-VL-3B-Instruct-Q4_K_M.gguf` | `hf-mirror.com/ggml-org/...`（HuggingFace 官方 GGUF 转档） | 1.8 GB |
| `mmproj-Qwen2.5-VL-3B-Instruct-Q8_0.gguf` | 同上（视觉投影器，缺它模型看不见图） | 806 MB |

合计约 **2.7 GB**，全在 `D:/峤的个人档案/做点东西/_vlm_local/`（项目目录外，不污染交付物）。

调用只有一条命令，不需要 Python、不需要服务、不需要 key：

```bash
llama-mtmd-cli.exe -m Qwen2.5-VL-3B-Instruct-Q4_K_M.gguf \
  --mmproj mmproj-Qwen2.5-VL-3B-Instruct-Q8_0.gguf \
  --image chart.png -p "问题" -n 200 --temp 0 -t 8 --image-min-tokens 1024
```

> `--image-min-tokens 1024` 不能省。日志里 llama.cpp 明确警告：`Qwen-VL models require at minimum 1024 image tokens to function correctly on grounding tasks`。

### 2.2 测了什么图

自造一张 a–F 图，**真值已知**（否则测完无法判断对错）：

- 第一段：F 0→6，a 0→2，**斜率 1/3**
- 第二段：F 6→10，a 2→4，**斜率 1/2**
- 折点 **(6, 2)**；第二段外推至 F=0 得 **a 轴截距 −1**
- 物理含义：M=2 kg、m=1 kg、μ=0.2、g=10（对应 B-20 那类题的三步反推）

### 2.3 四问结果

| # | 问题 | 模型答 | 真值 | 判定 |
|---|---|---|---|---|
| Q1 | 横纵轴各是什么量、什么单位 | 力（N）／加速度（m/s²） | 同 | **✓** |
| Q2 | 折线几段、折点坐标 | 2 段，**(6, 2)** | 同 | **✓** |
| Q3 | 两段斜率各是多少 | **1/3 与 1/2**（读出 (0,0)(6,2)(10,4) 后自算） | 同 | **✓** |
| Q4 | 第二段延长线与纵轴交点 | **2** | **−1** | **✗** |

Q3 的原文回答：

> 斜率 = (2−0)/(6−0) = 2/6 = 1/3；斜率 = (4−2)/(10−6) = 2/4 = 1/2

### 2.4 Q4 为什么错——这是本次最有价值的发现

它答 2，正好是**折点的纵坐标**。也就是说它没有做「向左延长到 F=0」这个几何动作，而是就近取了一个图上现成的数。

但换个问法：

> 已知直线过 (6,2) 和 (10,4)，斜率 k=0.5。求 b 使 a=kF+b，只输出 b 的值。

**答：−1 ✓**

**结论：模型的读数能力和代数能力都在，缺的是「把几何动作拆成可执行步骤」的脚手架。** 直接问截距，它会退缩到"取一个看得见的数"；把两点摆出来，它算得完全正确。

这条对工程的直接含义：**不要期望一句 prompt 出答案，要把读图拆成「先报关键点 → 再代数计算」两段**。这与项目里 L1/L2 分层校验的思路是同一个道理。

### 2.5 速度与资源

| 项 | 实测 |
|---|---|
| 单问耗时 | **40–56 秒**（含每次重新加载模型约 20 秒） |
| 视觉编码 | 9.8 秒/张（1024 token） |
| 内存占用 | 模型 1.8 GB + mmproj 0.8 GB，13.8 GB 内存下无压力 |
| 提速手段 | 用 `llama-server.exe` 常驻可省掉每次重载的 ~20 秒（未实测） |

## 3. 纯 PIL 像素扫描（更准，但需要定标）

不需要任何模型和额外包，只用已装的 Pillow。做法：按颜色筛出折线像素 → 用已知轴像素位置反算 (F, a) → 分段最小二乘。

实测（同一张图）：

| 量 | 提取值 | 真值 | 误差 |
|---|---|---|---|
| k₁ | 0.3346 | 0.3333 | **0.4%** |
| k₂ | 0.4990 | 0.5000 | **0.2%** |
| 截距 b₂ | −0.9898 | −1.0000 | **1.0%** |
| 反推 M+m = 1/k₁ | 2.989 | 3 | 0.4% |
| 反推 M = 1/k₂ | 2.004 | 2 | 0.2% |
| 反推 μ = −b₂M/(mg) | 0.198 | 0.2 | 1.0% |

**代价**：轴的像素位置与数值范围必须由外部给定（本次是硬编码，因为图是我自己画的）。真实考题图要自动定位轴和刻度，这一步比拟合难得多。脚本 `pixel_digitize.py` 在 `_vlm_local/`。

**定位**：它适合做**金标准**（验证 VLM 读数对不对），不适合做自动化主力。

## 4. 走不通的路，以及为什么

| 方案 | 为什么不行 |
|---|---|
| `pip install numpy` / `plotdigitizer` / `opencv-python` | **本机安全策略直接拦截**（命令被拦，Sandbox 未返回资源，按规则不重试）。所以所有依赖 numpy/scipy 的方案（含 plotdigitizer、deplot、ChartQA）在本机**当前配置下不可用** |
| torch + transformers 跑 HF 原版权重 | 同上（装不上），且无 GPU |
| 7B 级 VLM | 内存 13.8 GB，Q4 需 16 GB 起，**不够** |
| Ollama / LM Studio | 未实测。它们是 llama.cpp 的封装，能跑但**要额外装软件**；本次选 llama.cpp 官方二进制是因为它零安装、零网络依赖 |

## 5. 必须声明的空白

1. **测的是合成干净图，不是真实扫描件。** 我这张有规整网格、清晰刻度、单一颜色折线。真实考题图有扫描噪点、多线交叉、密集标注、手写批注，精度会下降——**降多少我没测**。
2. **B-20 的原图至今没有。** 工作区 0 张图片。所以「本方案对 B-20 是否成立」还是未知，只能说「在一张结构类似的合成图上成立」。
3. **只测了 a–F 一种图型。** v–t 图、几何受力图、装置示意图都没测。
4. **A-02 的 v–t 图数值（B 碰前速度 1.2v₀）未测**——那也是「图即数据源」。
5. **未验证多图输入**（`--image` 支持逗号分隔多个文件，但没有实测）。
6. **中文标注识别只被试过一处极短标签**（"a/(m·s⁻²)"、"F/N"），长句图注未测。

## 6. 对项目的落地建议

| 用途 | 建议 |
|---|---|
| 评测层补图（T12b） | **用 llama.cpp 本地跑**，不依赖 deepseek 视觉接口，也不改变 `answer.schema.json`。评测层只需加 `input_modality` 元数据 |
| 提示词结构 | **必须两段式**：先让模型报关键点坐标，再单独让它算。直接问最终量会失败（Q4 已证） |
| 造金标准 | 用纯 PIL 像素扫描（误差 0.2–1%），人工给定轴定标 |
| B-20 归类（N2） | 本方案使「有图输入」可测，B-20 应从 `countable=0` 恢复为可统计——**但前提是先取到 B-20 原图并复现本测试**，现在还不能改 |
